Тема проекта

Сервис для совместного планирования поездок - Trip planner

Описание: Единое цифровое пространство для туристической группы, которое будет объединять все этапы планирования и проведения поездки: от первой идеи до финальных расчетов. Можно создавать маршрут, добавлять точки интереса, отмечать бюджет, распределять затраты, голосовать за варианты.

Технологический стек

Backend – Python

Frontend - TypeScript, JavaScript

База данных - PostgreSQL, PL/pgSQL

Контейнеризация - Docker, Docker Compose

Внешние API - OpenStreetMap Nominatim

Общее описание 

Проблема
	Группе людей сложно спланировать маршрут и расписание совместной туристической поездки из-за большого количества предложений от каждого из участников. Возникающие в ходе обсуждения варианты быстро теряются в общих беседах группы, из-за чего тяжело обсудить и учесть предпочтения каждого человека
Требования
•	Когда кто-то из моих друзей предлагает посетить ещё одно место, я хочу видеть это предложение и иметь возможность проголосовать за или против него, чтобы каждый был в курсе предложения и вопрос изменения маршрута решался мнением большинства.
•	Когда я добавляю все желаемые места на карту, я хочу видеть их реальное географическое расположение, чтобы оценить, сколько времени уйдет на перемещения, и логически сгруппировать посещения по дням и районам
•	Когда я оплачиваю что-то, связанное с поездкой, не только за себя, но и за кого-то еще, я хочу видеть автоматическое распределение долга между участниками, чтобы каждый сразу знал кому и сколько он будет должен
Разработка архитектуры и детальное проектирование
Характер нагрузки на сервис
Соотношение R/W нагрузки:
Чтение (Read): ~70% (просмотр поездок, маршрутов, расходов, мест, голосований)
Запись (Write): ~30% (создание поездок, добавление расходов, голосование, создание маршрутов)
	
Объёмы трафика:
- Пользователи: 10к активных пользователей в сутки
- Запросы в секунду: 500 RPS в пике
- Размер ответов: 25 KB (JSON данные)
- Пиковые периоды: планирование поездок (вечера, выходные) 

Объёмы дисковой системы:
Для обеспечения устойчивой работы рекомендуется выделить 500GB – 1 TB дискового пространства.

Рис. 3 Схема базы данных
Схема масштабирования сервиса при росте нагрузки в 10 раз
1. Вертикальное масштабирование (краткосрочные меры):
API Gateway (Nginx/Kong):
CPU: 8-12 ядер
RAM: 16-24 ГБ
SSD/NVME диски
Микросервисы (каждый инстанс):
CPU: 4-8 ядер на сервис
RAM: 8-16 ГБ на сервис
Количество инстансов: 3-5 на каждый ключевой сервис (Trip, Map, Voting)

База данных PostgreSQL:
CPU: 16-24 ядра
RAM: 64-128 ГБ
SSD NVME с RAID 10

2. Горизонтальное масштабирование (архитектурные изменения):
Балансировка нагрузки:

Внешний балансировщик (AWS ALB/Google Cloud LB) → внутренние балансировщики на каждый сервис
5-10 инстансов каждого микросервиса за балансировщиком
Автоскейлинг по CPU/RPS метрикам

База данных:

PostgreSQL шардинг:
Шардинг таблиц по user_id (например, 64 шарда)
Использование Citus для распределенного PostgreSQL
Мастер для записи + 4-6 реплик для чтения
Читающие реплики распределены географически (если нужно)

Кэширование:

Redis Cluster из 9 нод (6 мастера, 3 реплики)
Локальный кэш (Caffeine) в каждом инстансе приложения
CDN для статических картографических тайлов

3. Оптимизация хранения данных:
PostgreSQL партиционирование:
trips таблица: партиционирование по дате создания (помесячно)
votes таблица: партиционирование по trip_id (range partitioning)
debts таблица: партиционирование по году расчета

Архивация и холодное хранение:

Архивация завершенных поездок (>2 лет) в S3/Яндекс Object Storage
Старые голосования (>1 года) → в колоночное хранилище (ClickHouse) для аналитики
Логи и метрики → в Elasticsearch + долгосрочное хранение в S3
